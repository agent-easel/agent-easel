# Typed requester-bound reply confirmation replaces the Confirm button; listed bots may start Runs

The earlier Chat control access decision ([#285](https://github.com/alimek/t3-factory/issues/285)) made every Start, Human answer and Archive wait for a **Confirm** button that only the requester could click within five minutes. A separate agent that grills a spec with people in a Discord thread then needs to ask Factory, in that same thread, to start a Flow and to read the result there. Discord bots cannot click buttons, and Chat control ignored every bot-authored message. This record partly supersedes #285: its default-deny Access, requester-only consent, binding to exact parameters, five-minute lifetime, single use and the rule that the language model never authorizes itself all stay; the button as the consent gesture and the human-only requester do not.

A review's last message now mentions the requester and shows an exact confirmation phrase, `confirm` followed by a fresh four-character code. The requester confirms by sending a Discord Reply to that message whose text is exactly the phrase. Factory decides this deterministically from its own records before any model call: the message must reference that review's last message, come from the requester, match the phrase, arrive within five minutes of the review and find the review unused. It then rechecks On, Access, the Project grant, current Discord access and the frozen parameters as the button did. A typed Reply is a gesture both people and bots can make, so one consent path serves both; the code's alphabet leaves out characters that are easily confused, and any message shaped like a phrase, or replying to a review's last message, never reaches the model. The review's last message is edited to **✅ Confirmed**, **⌛ Expired**, **↩️ Replaced** or **🚫 No longer valid** when it can no longer confirm anything. There is no dual path: the button, its interaction handling and its tests are removed, and reviews still waiting for a click when Factory is upgraded expire, so their requesters ask for a fresh review.

A per-user "no confirmation required" flag was rejected. The model sits between the request and the action, so skipping consent would let a misread Flow, Project or prompt run unchecked; the phrase keeps a deliberate, exact step at the point where the reviewed parameters are frozen, for bots as much as for people.

Access gains a separate Bots list. A listed bot may converse through the read tools and propose and confirm its own Starts, but never Human answers or Archive, which keep a Flow's human gates and irreversible actions human-only. Webhooks, unlisted bots and Factory's own account stay ignored. Bot messages are admitted only when they mention Factory's bot or are the confirmation Reply to the bot's own pending review, and loop and rate guards stop runaway bot conversations before any model call. Keeping bots in their own list, refused when Discord says an ID belongs to the other kind, avoids granting a bot human authority by mistake.

The requesting thread is the Run's originating thread for bot and human requesters alike. Completion notices now name the settlement kind and the exact Finish ending name, reversing their earlier omission: an agent continuing after a Run must tell which ending was reached, and prose alone would invite guessing. Attention, completion and Archive notices also carry one versioned single-line JSON record with a stable event identity, so a consumer can parse and deduplicate them while treating titles and ending names as data.
